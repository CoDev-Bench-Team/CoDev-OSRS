## 2. Not applied — a fifth request status, `Received`, and a signed completion (constitution IV; ADR-0007)

The `Request Status` component gained a variant, **`Received`**: `#ff8d28` ink
on a 10% tint of the same colour. A new **Status Definitions** table on the
components page defines it, and it redefines `Completed` along with it:

| Status | Definition as drawn |
|--------|---------------------|
| Received | "The Employee has received the item(s) — either picked up or delivered." |
| Completed | "The Employee has signed the **Accountability Form** and the request is fully closed." |

The new `04.1 - My Requests - View Request` frames draw the Employee's side of
that:

- a **five**-node status timeline, where the 09-22 file draws four
- a **Complete Request** section with a **Sign accountability form** link
- an **ACKNOWLEDGEMENT** panel: ten numbered conditions (salary deduction for
  loss, return on termination, IT audit and remote access, and so on), an
  **I have read and agree to the above** checkbox, **Type full name to sign**,
  **Other Notes**, and **Cancel** / **I acknowledge and sign**
- line items carrying per-unit tags (`CODEV- LAPTOP-0212`,
  `CODEV-KEYBOARD-0165`) instead of quantities

`Status changed email - For completion` then says "This is a confirmation that
your request … is now complete. The equipment listed below has been
successfully picked up/delivered."

**Why it is not applied.** Three governing documents say otherwise, and the file
contradicts itself:

1. Constitution 3.0.0 IV lists the statuses and has no `Received`.
   `RequestStatus` in `src/shared/ui/status.ts` makes an illegal state
   unrepresentable, so adding one is a type change for every screen.
2. ADR-0007 and FR-012a say `Completed` is set **by the Admin** and that **no
   actor** gets a confirm-receipt action. A signature from the Employee *is* a
   confirm-receipt action. It brings back the step ADR-0007 retired, and it
   moves the transition to the Employee.
3. The Admin's `02.2.1 - … Update Status` (2) frame is **unchanged** and still
   draws the Admin's **Complete** button. The file now has the Admin completing
   in one frame and the Employee completing in another.
4. The accountability form signs for **units** (serial-tagged items). That is
   the per-unit register constitution VIII puts out of scope (see §4).

**Open for the project owner**: adopt `Received` plus an Employee-signed
completion? If yes, it is constitution **4.0.0**: IV is redefined, ADR-0007 is
superseded, FR-012/FR-012a are rewritten, and stock rule 7 has to say which of
`Received` or `Completed` consumes stock. If no, the designer has to reconcile
the two completion frames.

The Status Definitions table has stale copy of its own. It is **not** a source
for any of the above:

- It names **Approver** and **Supply Admin**, the two roles ADR-0005 retired.
- It says approving means "Inventory is automatically deducted". Under
  constitution III, submitting reserves stock and approving changes no quantity.
- It gives `For Delivery` and `Received`'s neighbour the same sentence, "The
  item(s) are being sent to the Employee.", twice.
- It still carries the 2026-09-15 cancellation sentence that
  [drift-2026-09-22 §6](drift-2026-09-22.md) overtook.

## 3. Not applied — an Admin email on submit (constitution V; process-flow §1)

`New Request awaiting approval` is a new email to the **Admin**: "A new request
needs your approval.", requester and office, the lines, the **Note to
Approver**, and a **Review Request** action. `docs/process-flow.md` sends
submit's **Request received** to the Employee only. The recipient table in
constitution V does not list this template.

The SPA sends no mail. This is a backend and notification-catalogue decision.
**Open for the project owner and the backend team**: add the template, and the
Admin as a submit recipient?

`Status changed email - For completion` depends on §2. The redrawn received /
approved / declined emails move copy and layout only; they change no
transitions.

## 4. Not applied — Inventory becomes a unit register (constitution VIII; ADR-0006)

Eight new `03 - Inventory` frames manage **units**: *Delete Unit*, *Delete Unit
Confirmation*, *Bulk Add Units*, *Review/Edit*, and a status dropdown over the
`Inventory Status` component. That component gained **Assigned**,
**In Storage**, **Reserved** and **Inactive**; the last three are per-unit
states. This is the register [drift-2026-09-22 §4e](drift-2026-09-22.md)
recorded as anticipated and out of scope. It is still out of scope. The 09-22
§4d question of which Inventory is real is now sharper, because the file has
more unit-level frames than stock-level ones. Owned by BEN-48, which is already
blocked on it.

`Inventory Status` still paints every label `#2e7e47`, including the new
variants (09-22 §9, unresolved).

## 6. Accepted 2026-09-24 — `Ready for Pickup`, and pink and blue handover pills

Every frame drawn since 09-22 that shows a handover status paints it as the
`Request Status` component does: **For Delivery** `#ef5da8` on 10% pink and
**Ready for Pickup** `#235ea7` on `#edf5ff`. That covers the new My Requests
list and the Status Definitions table. ADR-0007 put both in the green `ready`
tone and kept the pink and blue pairs in the token layer, unused, "pending that
component's rework". The rework has come back with the colours kept and the
label still `Ready for Pickup` against the queue chip's `For Pickup`.

**Resolution — decided by the project owner, 2026-09-24.** Two decisions:

- **The state is `Ready for Pickup`**, as the `Request Status` component names
  it, and the queue's `For Pickup` chip is ignored. 09-22 §3 had taken the chip
  as authoritative; that is reversed.
- **The drawn pills are used.** `For Delivery` is `--color-status-delivery-*`
  (pink) and `Ready for Pickup` is `--color-status-pickup-*` (blue). The other
  five pills already match the drawn screens' solid fills, so they are
  unchanged. The component draws flat 10% tints of the ink; the screens paint
  the solid tints the token layer holds, and the screens are what ship.

Carried by constitution **3.0.1** (IV wording), the ADR-0007 amendment, spec 001
Session 2026-09-24, and spec 004 amendment 4.

## 7. Accepted — the Requests Queue list, unchanged since 09-22

`02 - Requests Queue` and its sort menu were not edited after the baseline.
What they draw was accepted in [drift-2026-09-22 §2–§3](drift-2026-09-22.md) and
is the source for spec 004's 2026-09-24 third amendment:

- summary cards; the queue frame draws two, and the review frames add
  *Low stock alerts*
- search, placeholder `Search by request ID,  employee name, email, or item...`
  (the double space is the file's; the port uses one)
- a sort select: `Newest First` · `Oldest First` · `Employee (A-Z)`
- filter chips: `All requests (238)` · `Pending Approval` · `Approved` ·
  `For Delivery` · `For Pickup` — the last one is built as **`Ready for Pickup`**
  (§6). `All requests` is active in `#cc2f4a` with a white label;
  the rest white with a `#e3e6ec` ring, `#172033` label and `#8a8f9c` count; 31px
  high, pill radius, 14×8 padding, 10px gap
- a table over **every live status**, not only pending rows. The sample rows mix
  `Pending Approval` and `Approved`, and every row carries **Review**
- pagination: `1-50 of 1,250` in `#313131`, then Back / pages / Next and
  `Result per page` = 50, all built from the `pagination *` components (36px
  high, r4, `#e9e9e9` ring, `#f4f4f4` hover, bold white numerals on the active
  page). The component caches the active page's fill as black, but the queue's
  instance binds it to the `Codev Red` style (`#cc2f4a`), and the style wins
  (09-22 §9)
- summary cards: 262x75, padding 22px sides and 8px top/bottom, 7px gap —
  shorter than the UI kit's 103px card
- summary values: the queue binds only *Pending approval* to red. *In
  Processing* and *Low stock alerts* bind to `Ink-900`

The queue frame draws no `Pending Approval` section heading over the table.
That heading came from the retired 2026-09-12 approver screen.

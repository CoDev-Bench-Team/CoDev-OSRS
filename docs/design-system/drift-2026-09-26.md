## How this was read

The method is the same as 09-22 and 09-24. A `.fig` is a zip whose
`canvas.fig` is Figma's kiwi binary: `fig-kiwi` magic, a version, then
length-prefixed blocks. Block 0 is the compiled schema (raw deflate) and block 1
is the document (zstd). The 09-24 file is no longer on disk, so this is not a
node-by-node compare. Every node's `editInfo.lastEditedAt` / `createdAt` after
**2026-09-24T05:59:31Z** (the baseline's export time) is rolled up to its owning
top-level frame. A frame with no node edited after that instant is unchanged.

Two reading rules apply to every port and every later diff:

1. **The style is the authority, not the cached value**
   ([drift-2026-09-22 §9](drift-2026-09-22.md#9-the-stale-cache-trap-reached-the-text-layer)).
   Resolve `styleIdForText`, `styleIdForFill` and `styleIdForStrokeFill` before
   reading `fontSize`, `fontName` or `fillPaints`.
2. **In a frame that draws a side panel over a page, only the panel is
   authoritative.** The page behind it is backdrop, and the designer does not
   keep it current. Set by the project owner, 2026-09-26. It is why the
   stock-line table behind `03.1 - Inventory - Add Inventory` is not evidence
   for Inventory frame B (§2), and why the Inventory header behind the eight
   `03.1 Add Asset - …` panels is not Assets copy (§4, #9).

[ADR-0008](../adr/0008-per-unit-inventory-register.md). Stock per
(asset, office) becomes counts of units by status, and the numbers are the same
as under 3.0.1.

Two details the SPA must not paper over (constitution VII):

- `Inventory Status` draws **`In Storage`**, which the contract's unit status
  set does not have.
- The removal confirmation asks for a **reason**. Whether the contract's
  unit-removal operation (planned as backend BEN-130) accepts one is not
  published.

## 3. Not applied — `Received` reaches the Employee's screens and an email (constitution IV; ADR-0007)

The three Employee frames edited on 09-26 each gained a `Status Timeline Item`
reading **Received**. Their timelines now have five steps:

`Submitted → Approved → For Delivery/For Pickup → Complete → Received`

In the timeline, `Received` comes **after** `Complete`. The Status Definitions
table (09-24 §2) defines it as happening before `Completed`. The file disagrees
with itself on the order.

`Status changed email - Received` (new, 09-25) has the eyebrow **"Equipment
Delivered/Claimed"** and the copy "Hi Maya - This is a confirmation that IT has
issued you these equipment. Before it's fully checked out to you, please re…".
It has a `Completed Sep 29, 2026, 9:42AM` row, an ITEM / QTY list, and the
action **Review & sign in the portal**.

**Not applied.** This is the accountability-form completion from
[drift-2026-09-24 §2](drift-2026-09-24.md#2-not-applied--a-fifth-request-status-received-and-a-signed-completion-constitution-iv-adr-0007),
and it is still the project owner's decision. Constitution 4.0.0 IV is unchanged
from 3.0.1, and FR-012a still forbids a confirm-receipt action.

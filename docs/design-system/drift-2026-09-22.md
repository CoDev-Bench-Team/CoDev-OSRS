looks for: re-vendor, diff, reconcile. This is the second such diff.

[drift-2026-09-15.md](drift-2026-09-15.md)
**Checked against**: `~/Downloads/Office Supplies Request System (OSRS).fig`,
exported **2026-09-22T03:18:01Z**, read directly rather than through the skill

**Status: accepted in full.** The project owner directed that the design file
wins and that the governing documents move to it. Constitution **3.0.0**,
`docs/process-flow.md`, `ARCHITECT.md`, spec 001 and ADRs 0005–0007 were
amended from this document. Nothing here was applied silently; every item below
names the amendment that carries it.

This export is a larger change than the last one. The previous one added a
status and some screens. This one changes **the shape of the domain**: what an
inventory record is, who does the fulfilment half of the pipeline, and how a
request ends.

## How this was read

Same method as last time, one format change. A `.fig` is a zip; `canvas.fig` is
Figma's kiwi binary: `fig-kiwi` magic, a version, then length-prefixed blocks —
block 0 the compiled kiwi schema (raw **deflate**), block 1 the document
(**zstd**). This export carries 645 schema definitions and **14,637 node
changes** across four pages (`Mockups`, `Prototype`, `Archive`,
`Internal Only Canvas`).

Two things made the diff precise rather than impressionistic:

- **`editInfo.lastEditedAt` / `createdAt` per node.** Rolling those up to the
  owning top-level frame gives an exact list of what moved since 09-15, and
  distinguishes *new* frames from *edited* ones. 3,238 nodes were touched on or
  after 09-17; 2,912 of them did not exist at the baseline.
- **Local style bindings beat cached values.** §7 of the last drift document
  found 69 of 822 bindings disagreeing with the style they point at. The same
  trap is in the **text** layer here, and it is why `02 - Catalog` looks broken
  if you read node properties naively — see §9.

## 2. Accepted — the role model collapses to two (constitution 3.0.0 II; [ADR-0005](../adr/0005-two-role-model.md))

`Top Navigation`'s Admin variant now reads **Requests Queue · Assets ·
Inventory · History**, and its account cluster identifies *Ethan Cruz, Admin*.
The queue that variant lands on is titled **Requests Queue** and subtitled
**"Review, approve, and fulfill supply requests"**.

That is one screen, one role, doing both halves of the pipeline:

| Panel | Actions it offers |
|-------|-------------------|
| `02.2 - Requests Queue - Review` | **Reject Request** · **Approve Request** |
| `02.2.1 - … - Review - Approve` | **Update Status** |
| `02.2.1 - … - Review - Update Status` | `Status *` select → **Update Status** |
| `02.2.1 - … - Review - Update Status` (2) | **Complete** |
| `02.2.2 - … - Review - Reject` | `Reason for rejection *` → **Confirm Rejection** |

The last drift document kept the split and recorded the merged bar as something
"spec 003 D1 already overrides". That override is withdrawn. The file has now
drawn the merged role three separate times — the bar, the queue subtitle, and a
single review panel that approves *and* fulfils — and the project owner has
accepted it.

**Resolution.** Two human roles: **Employee** and **Admin**. `Approver` and
`Supply Admin` are retired as distinct roles. ADR-0003 is superseded by
[ADR-0005](../adr/0005-two-role-model.md). Constitution II is redefined;
`docs/product.md`'s actor table and `ARCHITECT.md` §7 follow.

**What this costs, recorded so it is not rediscovered.** The control point
ADR-0003 existed to protect — that the person who judges necessity is not the
person who releases stock — is gone. One Admin can approve their own
department's request and hand over the item. That is the design's call, not an
oversight of ours; it is written down here so that a later decision to restore
the split is a deliberate reversal rather than a surprise.

## 3. Accepted — the request state machine ends differently (constitution 3.0.0 IV; [ADR-0007](../adr/0007-fulfilment-status-vocabulary.md))

The `Status Timeline` component and the Update Status panel agree on a
four-step lifecycle:

```
Submitted → Approved → For Delivery / For Pickup → Complete
```

Three changes against constitution 2.0.0:

| Was | Now | Evidence |
|-----|-----|----------|
| `For Release` then `Released`, two states | **one** handover state, chosen as **`For Delivery`** or **`For Pickup`** | `Status *` select offers them as alternatives; the timeline's third node is the single label "For Delivery/For Pickup" |
| `Released → Completed` by the **owning Employee** confirming receipt | **`Complete`**, pressed by the **Admin** in the Update Status panel | `02.2.1 - … - Update Status` (2) draws a single **Complete** button in the admin panel; no confirm-receipt control exists anywhere in the file for the employee |
| `Ready for Pickup` and `For Delivery` are *labels* on `Released` (spec 002 D5) | they are **states** | `Requests Queue` filters by them: chips read `All requests (238) · Pending Approval (7) · Approved (7) · For Delivery (7) · For Pickup (7)` |

The employee's `04.1 - My Requests - View Request` panel confirms it from the
other side: its only action is **Cancel Request**. There is no confirm-receipt
button on the employee's own request.

**Resolution.** The status vocabulary becomes:

`Pending Approval` → (`Approved` | `Rejected`) → (`For Delivery` | `For Pickup`)
→ `Completed`, with `Cancelled` reachable from `Pending Approval`, `Approved`,
`For Delivery` and `For Pickup`.

`For Release` and `Released` are retired. FR-012 (employee confirms receipt) is
withdrawn; FR-012 now gives `Completed` to the Admin and FR-012a forbids a confirm-receipt control. `src/shared/ui/status.ts`
follows; `Status/Ready for Delivery` in the token layer is the pair for
`For Delivery`.

**Flagged to the designer.** The `Request Status` component still carries a
pill labelled **"Ready for Pickup"** (`#235ea7` on `#edf5ff`) *and* one
labelled **"For Delivery"** (`#ef5da8`), while the queue's filter chips say
**"For Pickup"** and **"For Delivery"**. Three labels, two states. The chips are
taken as authoritative because they are the ones bound to a filter; the pill
component needs its `Ready for Pickup` variant renamed. The symbol is also
misspelled `Property 1=For Dellivery`.

## 4. Accepted — Assets and Inventory are two different things (constitution 3.0.0 III; [ADR-0006](../adr/0006-assets-and-inventory.md))

This is the largest change in the export, and the one that most invalidates
existing tickets. The Admin bar now has **two** data destinations where the
baseline had one.

### 4a. `Assets` — the requestable catalogue, by model

Title **Assets**, subtitle **"Deployed and available units"**, primary action
**+ Add Asset**.

| Column | Sample |
|--------|--------|
| ITEM NAME | Dell Latitude 7440 |
| CATEGORY | Laptops |
| MODEL | Latitude 7440 |
| AVAILABLE UNITS | 12 |
| PENDING/RESERVED UNITS | 4 |
| DEPLOYED UNITS | 3 |

Chips: `All assets (238) · In stock (7) · Low stock (7) · Out of stock (7)`.
Search placeholder: "Search inventory by item name or code". Category select:
"All categories". Pagination: `1-50 of 1,250`, Back / numbered pages / Next,
plus "Result per page" at 50.

### 4b. `Inventory` — stock levels, per item, per office

Title **Inventory**, subtitle **"Monitor stock levels, manage reservations, and
keep office essentials ready."**, primary action **+ Add Inventory**.

| Column | Sample |
|--------|--------|
| ITEM NAME | Dell Latitude 7440 |
| CATEGORY | Laptops |
| TOTAL STOCK | 32 |
| AVAILABLE QUANTITY | 18 (green; red at 0) |
| RESERVED / PENDING | 14 |
| STATUS | `In Stock` / `Low Stock` / `Out of Stock` pill |
| ACTION | **Update stock** |

Chips: `All items (238) · In stock (7) · Low stock (7) · Out of stock (7)`.

**`RESERVED / PENDING` is the part that changes the domain.** Spec 001's Out of
Scope list says, in as many words, "Separate reserved-vs-on-hand stock columns".
The design now has three numbers per item — total, available, reserved — and
the arithmetic `TOTAL = AVAILABLE + RESERVED` holds in every drawn row
(32 = 18 + 14, 24 = 8 + 16, 40 = 24 + 16, 28 = 4 + 24, 20 = 5 + 15,
60 = 0 + 60).

That is a different inventory rule from ADR-0002. Submitting no longer
*decrements stock*; it **moves quantity from available to reserved**. Total
stock is unchanged by a request until the items actually leave, which is what
`DEPLOYED UNITS` on the Assets screen counts.

### 4c. `03.4 - Update Stocks` — stock is held per office

Opened from a row's **Update stock**. A right-hand panel over the Inventory
table:

- read-only **Item Name** and **Category**
- a link, **"Update Item Details and Specs >"**
- section **STOCKS**: **Low-stock threshold** (numeric, sample `5`), then one
  stepper row per office — **Cebu**, **Bacolod**, **Makati**, **Ortigas**,
  **Davao** — each `−` / value / `+`
- **Cancel** / **Save Changes**

So on-hand quantity is a **vector over five offices**, not a scalar, and the
Catalog's toolbar carries a matching office selector reading **"Cebu Office"**.
The `Site Office Label` component has exactly those five variants.

**`Ortigas` replaces `Pasig`.** The published `CreateAssetDto` documents the
office enum as `Cebu | Bacolod | Makati | Pasig | Davao`
(`specs/001-office-supplies-mvp/contracts/README.md`). The design file says
`Ortigas`. **Flagged to the designer and to the backend team** — one of the two
has to move, and the SPA must not invent a third spelling.

### 4d. The two competing `03 - Inventory` frames

There are two frames named `03 - Inventory`, side by side, with identical
headers, subtitles, search, chips and **+ Add Inventory** button, and different
tables:

| | Created | Last edit | Columns |
|---|---|---|---|
| **A** @(728, 16721) | 09-14 13:46 | 09-19 04:57 | PR · ASSET · CATEGORY · ASSIGNED · OFFICE · ACTION (*Review*) |
| **B** @(2208, 16721) | 09-19 04:11 | 09-19 04:14 | ITEM NAME · CATEGORY · TOTAL STOCK · AVAILABLE QUANTITY · RESERVED / PENDING · STATUS · ACTION (*Update stock*) |

### 4e. What `+ Add Inventory` opens is a **unit**, not an item

`Add Catalog Item - Laptop`, a 400×1566 panel:

| Section | Fields |
|---------|--------|
| BASICS | Image (drop/browse, `.jpeg`/`.png`, max 25 MB) · Item name \* · Category \* · Description |
| PURCHASE DETAILS | Price · Supplier · Purchased Date |
| SPECS | Serial Number · Model · RAM · Storage · Processor · Graphics · Operating System · BitLocker Identifier · Recovery Key/PIN |

A serial number, a BitLocker identifier and a recovery key belong to **one
physical machine**, not to a stock line. Together with Inventory variant A's
`PR` code (`CODEV-LAPTOP-1232`), its `ASSIGNED` column, and Profile's
`Currently Assigned` list of tags (`CDV-MS-00087`, "Assigned Jan 14, 2026"), the
file is describing a **per-unit asset register** underneath the stock numbers.

**Recorded, not specced.** The MVP takes the aggregate model — Asset (a model)
with per-office stock — and treats the unit register as a **post-MVP capability
the design anticipates**. Building serial-number tracking, assignment and
BitLocker escrow is not a four-week job and nothing in the request pipeline
needs it. What the MVP *must not* do is design a schema that forecloses it.
**Flagged to the designer**: `+ Add Inventory` currently opens a per-unit form
from an aggregate table, which is the one part of this that cannot be built as
drawn.

**Resolution.** The catalogue becomes four transactional templates —
**Request received**, **Request approved**, **Request declined**, and a generic
**Status changed** that carries any other transition as a from/to pair — plus
two non-transition templates, **Welcome** (account created) and
**Action required**. Constitution V is redefined: every defined transition still
MUST send mail, but `Status changed` is allowed to be the template for more than
one of them. The invented "Request Cancelled" copy from the 2026-09-15
amendment is **withdrawn**; cancellation now sends `Status changed`.

**`Action required` is a new capability, not a new template.** It presupposes
that a reviewer can ask the requester for a detail and set a **Respond by**
date, and that the request can be "closed" if they do not answer. No screen in
the file lets anyone raise such a request, and no status covers it. **Recorded
as out of scope for the MVP and flagged to the designer** — the template is
real, the flow behind it is not drawn.

Two smaller facts worth keeping:

- The emails say **`REQ-10482`**; every SPA screen says **`REQ-2026-1847`**.
  Two request-id formats. **Flagged.**
- `Status changed email` carries a **Pickup** row — "6th floor IT desk". That
  is the pickup location spec 001 collects at release, so the field survives
  the state-machine change of §3 and is set when the Admin chooses

## 6. Accepted — cancellation always requires a reason (constitution 3.0.0 IV)

`04.2- My Requests - Cancel Request` draws the employee's own cancel dialog
with a field labelled **"Reason for cancellation \*"** — asterisked, placeholder
"e.g duplicate request..." — and buttons **Cancel** / **Confirm Cancellation**.

Constitution 2.0.0 made the reason *optional* for the owning Employee and
required only "by anyone other than the owning Employee". The 2026-09-15
amendment reasoned that the file's own sentence attached the requirement to a
non-requestor. That reasoning is now overtaken by a drawn dialog on the
employee's own screen.

**Resolution.** A cancellation reason is **required from whoever cancels**.
FR-009a loses "A reason is optional."

`04 - History`'s detail panel reads the stored reason back under the label
**"Reason for cancellation"** (sample: "Duplicate of request SR-1042"), matching
how `02.2.2.1` reads a rejection reason back under **"Reason for rejection"**
with a **Close** button.

## 9. The stale-cache trap reached the text layer

§7 of the last drift document found 69 of 822 local style bindings whose cached
paint disagreed with the style they point at, and warned that the export tool
reads the cache. The same disagreement is in the **text** styles, and
`02 - Catalog` is the clearest case:

| Node | Binds | Style says | Node caches |
|------|-------|-----------|-------------|
| `Supply Catalog` (title) | `H1` (12:124) | Space Grotesk Medium **32px** | **11.5px** |
| `Browse available equipment…` (subtitle) | `Body 1` (13:130) | Inter Regular **14px** | **32px** |
| `Inventory` (title) | `H1` (12:124) | Space Grotesk Medium 32px | 32px ✓ |
| `Monitor stock levels…` (subtitle) | `Body 1` (13:130) | Inter Regular 14px | 14px ✓ |

Catalog's two nodes hold each other's sizes. Read the cache and the screen
renders with a tiny heading over a huge subtitle; resolve the binding and it is
the same heading/subtitle pair as every other screen.

**The rule from the last document holds and is now general: the style is the
authority, the cached value is not.** Anyone porting a screen from this file —
or writing a renderer against it — must resolve `styleIdForText`,
`styleIdForFill` and `styleIdForStrokeFill` before reading `fontSize`,
`fontName` or `fillPaints`.

The brand red from §7 of the last document is **unresolved and still owed a
designer's call**: `Codev Red` is `#cc2f4a`, 24 nodes still cache `#c62828`, and
this export paints the Admin nav's current item and its count badge `#cc2f4a`
while the Employee variant beside it still paints `#c62828`. The `+ Add
Inventory` and `+ Add Asset` buttons are `#cc2f4a`; the `Update stock` link and
the `Save Changes` button on `Add Catalog Item` are `#c62828`. Two reds, still.

One more, smaller: `Inventory Status`' three variants — `In Stock`,
`Low in Stock`, `Out of Stock` — all paint their **label** `#2e7e47` (green),
including the amber and red frames. The `Stock status` pills actually used on
`03 - Inventory` paint correctly (`#16794a`, `#a15c00`, `#c62828`), so the
component is the thing that is wrong. **Flagged.**
